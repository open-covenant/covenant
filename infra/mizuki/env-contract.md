# Production environment contract

Live values belong in Render's encrypted settings and the operator password manager. Never commit addresses tied to a person, private keys, bearer tokens, webhook secrets, or signer mappings with personal labels.

The image-backed production runtime is the only commercial core and the only service attached to `mizuki-postgres`. Shadow, signer, updater, and deployment controller each have separate PostgreSQL databases and credentials. No component receives another component's database URL. The refund custody key, escrow custody key, and job-authority key must all be distinct.

Generate the job-authority seed once, store it immediately, and derive only its public key for the signer:

```sh
authority_seed=$(openssl rand -base64 32 | tr -d '\n')
MIZUKI_JOB_AUTHORITY_SEED="$authority_seed" pnpm --filter @covenant/mizuki build
MIZUKI_JOB_AUTHORITY_SEED="$authority_seed" pnpm --filter @covenant/mizuki job-authority-public
```

Store `authority_seed` as the API secret and the command output as the signer public key. Never reuse either Solana custody key.

The GitHub App needs repository Contents read/write, Issues read, Pull requests read/write, Checks read, and Metadata read. Subscribe only to Pull request events. Public v1 intake remains installation- and label-authorized; Mizuki never opens unsolicited PRs.

Reviewer runtime readiness is a non-billable authenticated `GET /v1/models` through the token-in-path proxy. It requires the exact reviewer model in the catalog, sends no marketplace routing or price headers, and does not claim to prove funding. The 23 August funded canaries qualified the original coding route and the independent `deepseek-v4-flash` review route; their redacted evidence is content-addressed at `https://raw.githubusercontent.com/open-covenant/covenant/main/infra/mizuki/evidence/usepod-route-2026-08-23.json#sha256=21bbff5860332305ec090c9bb8245de36e6e53819a97d29401724c5c3644c441`. On 24 August, the production coding route moved to `deepseek-v3.2` after a funded marketplace tool-call benchmark returned the canonical `deepseek.v3.2` identity, provider and request receipts, and a valid `read_file` call in 7.3 seconds. Never put a paid canary on `/readyz`. Every paid-job and contributor-patch review uses the same token-in-path, route, retention, and price-ceiling contract. Public review receipts retain the model, marketplace route, provider/request identifiers, and provider-reported cost when available, but never expose the remaining account balance.

The database initializes paid intake and new bounty claims as closed. Non-cacheable `GET /v1/admission` exposes the non-sensitive state. Only an authenticated operator may change it through `POST /v1/admin/admission`; every change requires a reason and the exact `expectedRevision`. Payment admission, new-claim binding, settlement recovery, and control mutation acquire the same PostgreSQL advisory lock, so rolling-process overlap cannot bypass closure ordering. A stale request that would transition either control from closed to open returns `409` without mutation; an impossible future revision is always rejected. A request that only closes controls may advance from a stale revision so emergency containment always wins over an in-flight open. Every committed revision is inserted in the same database transaction into an append-only audit table whose update, delete, and truncate operations are rejected by triggers; authenticated `GET /v1/admin/admission/audit` returns that ledger in revision order. Runtime predeploy also refuses to proceed unless both controls are durably closed. Enabling either control requires a fresh, complete `/readyz` report. Public quote, payment, and new-claim paths recheck readiness after reading the durable control, so an incomplete live configuration can serve liveness and public evidence but cannot issue a payable quote or admit work. A missing or unreadable control row blocks both paths. Existing jobs, refunds, active-claim PR submission, and disputes remain recoverable while new intake is paused.

`CLAWPUMP_PAYOUT_WALLET` is always linked to the signer escrow authority in the Blueprint. `CLAWPUMP_API_KEY`, `CLAWPUMP_AGENT_ID`, and `MIZUKI_TOKEN_MINT` remain unset until their operator-owned launch steps are complete. Before setting the agent ID, an operator must register the exact escrow authority through the ClawPump dashboard or `set_external_wallet` signed flow, retain the response, and verify one distribution against finalized chain history. Mizuki never receives the wallet private key. The earnings API is platform-reported accounting; only the escrow funding transaction proves bounty custody.

## Image-backed release targets

`mizuki-runtime-shadow` and `mizuki-runtime-production` are new services because changing an existing service to `runtime: image` is not a safe in-place migration. Shadow is private; production is a web service. Both are single-instance, have automatic deployment disabled, use the same `ghcr.io/open-covenant/covenant/mizuki@sha256:<digest>` baseline, and run `node dist/predeploy-cli.js`. Production alone uses the canonical `mizuki-postgres`; shadow uses `mizuki-runtime-shadow-postgres`. Never restore production data into shadow or open shadow admission.

The first image cutover happens with paid intake and claims closed. Reconcile the canonical database, deploy and probe the image runtime, point the website's `MIZUKI_API_URL` and proxy secret at that runtime through Blueprint service links, then suspend the old source-built API before reopening either gate. Verify the old public origin cannot accept a quote, payment, refund, claim, or webhook. Because both versions must never process commercial work concurrently, a failed cutover rolls the website back only while intake remains closed; it never reopens the old runtime against live traffic. No state copy is required: the canonical database stays in place throughout.

The committed all-zero digest is an intentionally non-deployable bootstrap sentinel, not an image version. Before the first Blueprint sync that creates either target, publish and verify one `linux/amd64` image through `mizuki-image.yml`, then replace both sentinel URLs with the same exact digest from its attested promotion input. Render's Blueprint schema cannot obtain `image.url` from `sync: false`, and it cannot create registry credentials. Pre-create the workspace credential named `mizuki-ghcr`; its GitHub Container Registry token needs package-read access only. Never replace the digest with a tag.

Production-owned provider, GitHub App, job-authority, signer, updater, live-payment, and production-probe settings are absent from shadow. `MIZUKI_RUNTIME_ROLE=shadow` makes the process reject any such setting, requires mock payments and disables the GitHub App, requires isolated durable storage, and prevents either admission control from being opened. Shadow retains only its own database, admin token, session secret, and web-proxy secret. Its private `/deployz` probe accepts exact `{ "ok": true }`, which proves the candidate booted, migrated and read its isolated database, and found both durable controls closed without giving candidate code an external authority.

`MIZUKI_DEPLOY_PRODUCTION_PROBE_TOKEN` is generated on the controller and linked only to production as `MIZUKI_RELEASE_PROBE_TOKEN`. The controller's route token is separate. Production `MIZUKI_PUBLIC_BASE_URL` follows its Render-provided `RENDER_EXTERNAL_URL`; set controller `MIZUKI_DEPLOY_PRODUCTION_PROBE_URL` to that exact HTTPS origin plus `/internal/mizuki/functional-readiness`. The fixed tokenless shadow probe is `http://mizuki-runtime-shadow:10000/deployz` on the private network.

The production functional probe checks every runtime readiness dependency except the updater. Operator `/readyz`, public-control opening, and paid-job admission continue to require the full updater-inclusive report. Updater readiness still authenticates the controller's complete `/readyz`, including strict production application probing, so the graph terminates at the independently cached functional scope without weakening deployment or rollback evidence.

The updater's `90000` deployment-hook timeout remains available to mutating promotion and rollback calls. It is not the core readiness allowance: a controller readiness traversal that does not finish inside the runtime's `15000` updater request budget fails the operator report closed.

The updater never receives signer custody, signer auth, treasury, x402, gateway, or API admin secrets. The API observes signed updater evidence with a read-only token; it cannot propose, approve, mutate promotion control, merge, deploy, or roll back an upgrade. Submission, control, read, and deployment-hook authorities are separate credentials. Promotion control is database-backed and closed by default. Missing proposal, review, GitHub App, or deployment-controller inputs do not prevent the private service from binding, migrating its database, and serving liveness; `/readyz` lists only missing variable names and remains `503`, proposal submission is rejected, recovery does not start, and promotion cannot be enabled. Once configured, readiness authenticates the App, validates each allowlisted repository installation through an exact one-repository token, resolves both pinned workflow identities through GitHub's Actions API, and authenticates the side-effect-free deployment-controller endpoint. Required checks must belong to the configured workflow run and signed pull-request refs; an unpinned same-name duplicate fails admission. The pinned workflow file must have the same Git blob at the signed base and candidate commits. Every signed proposal binds the protected base branch SHA; check admission and merge fail closed if that ref advances. The external release operator must enable an exact revision with a reason through authenticated `PUT /v1/admin/promotion-control`. One durable reservation is acquired before merge and retained through controller finalization or terminal rollback. Every ownership mutation is revisioned and append-only audited. A failed rollback retains the owner and closes control until explicit operator resolution; monitoring and rollback continue even if control is paused.

The Blueprint links the controller host and bearer credential directly from the private service. Confirm updater `/readyz` authenticates the controller before enabling a promotion revision.

Promotion hook success enters durable health verification. The production endpoint must report `environment: production`, the exact candidate and merge SHAs, the persisted promotion operation ID, and `active: true` for every healthy observation. Shadow evidence cannot satisfy this gate. Regression, timeout, or exhausted retries invokes rollback before the record can become `completed`.

The controller is a private service and accepts no service ID, Render URL, command, or executable input. It maps each strict updater request to one of two configured service IDs. Shadow always deploys the reviewed OCI digest to the dedicated shadow service. Promotion records the currently live production deploy before it deploys that same digest to production. Rollback uses Render's rollback endpoint with that recorded deploy ID and does not report completion until the rollback is live, active, and passes the authenticated application probe. The Postgres ledger reserves idempotency keys and action timestamps before every external mutation; after a restart, only one matching Render deploy can satisfy reconciliation.

The Render API key is account-wide rather than scoped to these two services. Use a dedicated account identity with the least workspace access available, then enforce the two exact IDs in all three controller settings. Record the IDs after the image targets exist; Blueprint updates ignore newly added `sync: false` values, so set or rotate these values explicitly in the Dashboard or authenticated API. Confirm the shadow ID resolves to a private image-backed service, production resolves to a web image-backed service, both report the configured repository and automatic deploys off, and controller `/readyz` succeeds. The updater uses the controller's one private origin and fixed `/v1/deployments/*` paths. Do not expose the controller as a public web service.

## Rotation order

1. Stop new paid intake and reconcile every accepted liability, job, escrow, and signer operation.
2. Rotate the signer bearer token through the Blueprint link and confirm unauthorized calls fail.
3. Rotate gateway and updater read tokens independently and repeat their negative authorization tests.
4. Rotate controller route authentication and the production application probe token separately; redeploy production after changing the linked probe value. Shadow has no probe credential to rotate.
5. Rotate the GHCR read credential, verify both pinned baseline digests remain pullable, then revoke the old credential.
6. Rotate GitHub App keys and webhook secret, then replay a signed delivery.
7. Rotate model, sandbox, ClawPump, RPC, and price-source credentials independently.
8. Rotate refund custody, escrow custody, and job authority separately. Update the matching public setting atomically and run both canaries again before reopening intake.
9. Record role, timestamp, old fingerprint, and new fingerprint. Never record secret material.
